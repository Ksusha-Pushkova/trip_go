# Trip Service

Лабораторная работа 2 — HTTP API, PostgreSQL и наблюдаемость.

Trip Service — HTTP-сервис для управления поездками. Он позволяет создавать поездки, получать информацию о них и завершать поездки. Данные хранятся в PostgreSQL.

## Возможности

* создание поездки;
* получение поездки по ID;
* завершение поездки;
* проверка состояния сервиса через `/health`;
* проверка доступности базы данных через `/ready`;
* валидация входных данных;
* ошибки в формате `application/problem+json`;
* запрет двух активных поездок одного водителя;
* атомарное создание записи в `trips` и `trip_status_history`;
* корректное завершение сервиса по сигналу;
* конфигурация через переменные окружения;
* логирование HTTP-запросов;
* обработка ошибок и восстановление после panic;
* распределённая трассировка и сбор метрик с использованием OpenTelemetry.

## Требования

* Go 1.26+
* PostgreSQL
* `goose` для миграций
* `tripgoctl` для управления учебным окружением

## Переменные окружения

Пример конфигурации находится в `.env.example`.

| Переменная | Назначение |
|---|---|
| `HTTP_ADDR` | адрес HTTP-сервера |
| `HTTP_READ_TIMEOUT` | таймаут чтения запроса |
| `HTTP_READ_HEADER_TIMEOUT` | таймаут чтения заголовков HTTP-запроса |
| `HTTP_WRITE_TIMEOUT` | таймаут записи HTTP-ответа |
| `HTTP_IDLE_TIMEOUT` | таймаут idle-соединения |
| `LOG_LEVEL` | уровень логирования |
| `SHUTDOWN_TIMEOUT` | время ожидания при graceful shutdown |
| `DATABASE_URL` | строка подключения к PostgreSQL |
| `DATABASE_MAX_CONNS` | максимальное количество соединений в пуле |
| `DATABASE_MIN_CONNS` | минимальное количество соединений в пуле |
| `DATABASE_MAX_CONN_LIFETIME` | максимальное время жизни соединения |
| `DATABASE_MAX_CONN_IDLE_TIME` | максимальное время простоя соединения |
| `DATABASE_CONNECT_TIMEOUT` | таймаут подключения к БД |
| `DATABASE_QUERY_TIMEOUT` | таймаут операций с БД |

Файл `.env` содержит локальные значения и не добавляется в Git.

## HTTP API

### Создание поездки

```http
POST /api/v1/trips

Content-Type: application/json
```

Пример запроса:

```json
{
  "user_id": "5cb72c04-7650-45c9-a79b-bcdba0631e0c",
  "driver_id": "8860b315-ec86-42eb-a17c-7c163d721ff5",
  "start_point": {
    "latitude": 59.9398,
    "longitude": 30.3146
  },
  "end_point": {
    "latitude": 59.9290,
    "longitude": 30.3626
  },
  "price": 1450
}
```

Успешный ответ:

```text
201 Created
```

### Получение поездки

```http
GET /api/v1/trips/{tripId}
```

### Завершение поездки

```http
POST /api/v1/trips/{tripId}/finish
```

При успешном завершении:

```text
200 OK
```

Повторное завершение уже завершённой поездки:

```text
409 Conflict

code: trip_completed
```

### Health check

```http
GET /health
```

Возвращает `200`, если HTTP-сервис запущен.

### Readiness check

```http
GET /ready
```

Возвращает:

* `200`, если база данных доступна;
* `503`, если база данных недоступна.

## Middleware

В HTTP-сервере используются middleware для обработки запросов:

* логирование HTTP-запросов;
* восстановление после panic;
* сбор данных для распределённой трассировки;
* сбор метрик.

Middleware позволяют вынести общую обработку HTTP-запросов за пределы бизнес-логики обработчиков.

## Наблюдаемость

Для наблюдения за работой сервиса используется OpenTelemetry.

В проекте предусмотрены:

* **Tracing** — сбор информации о прохождении запросов через компоненты приложения;
* **Metrics** — сбор метрик, позволяющих отслеживать работу сервиса.

Трассировка помогает анализировать выполнение запросов, а метрики — оценивать состояние и производительность приложения.

Дополнительная информация о настройке и использовании инструментов наблюдаемости находится в `docs/observability.md`.

## Ошибки

Ошибки возвращаются в формате `application/problem+json`.

Используемые коды:

| HTTP | Код | Причина |
|---|---|---|
| 400 | `invalid_request` | некорректное тело запроса или ID |
| 404 | `trip_not_found` | поездка не найдена |
| 409 | `trip_completed` | поездка уже завершена |
| 409 | `driver_busy` | у водителя уже есть активная поездка |
| 500 | `internal_error` | внутренняя ошибка |

## Архитектурные решения

### Менеджер транзакций

Используется интерфейс:

```go
type TxManager interface {
    Do(ctx context.Context, fn func(ctx context.Context) error) error
}
```

Менеджер:

* открывает транзакцию;
* передаёт её через `context`;
* делает `COMMIT`, если функция завершилась успешно;
* делает `ROLLBACK` при ошибке или panic;
* поддерживает вложенные вызовы `Do`, используя существующую транзакцию.

Репозиторий получает executor из контекста. Поэтому бизнес-логика не работает напрямую с `pgx` и не управляет транзакцией.

Для транзакций используется уровень изоляции `Read Committed`.

### Атомарность создания поездки

Создание поездки выполняется внутри одной транзакции:

1. добавляется запись в `trips`;
2. добавляется запись в `trip_status_history`.

Если одна из операций завершается ошибкой, транзакция откатывается целиком.

### Запрет двух активных поездок

Для `driver_id` используется частичный уникальный индекс, который запрещает наличие более одной активной поездки одного водителя.

Нарушение ограничения PostgreSQL с кодом `23505` проверяется дополнительно по имени ограничения `trips_driver_active_uniq`.

При нарушении этого ограничения ошибка преобразуется в доменную ошибку `driver_busy` и возвращается клиенту как `409 Conflict`.

Дополнительно проверена конкурентная нагрузка:

```text
1 201
19 409
```

То есть при 20 одновременных попытках создать поездку одному водителю создаётся ровно одна активная поездка.

### Завершение поездки

Завершение выполняется условным `UPDATE` только для поездки со статусом `active`.

Если обновление не затронуло строки, дополнительно проверяется существование поездки, чтобы корректно различить:

* `404 trip_not_found`;
* `409 trip_completed`.

Такой подход предотвращает race condition между проверкой статуса и изменением записи.

### Таймауты

Таймауты подключения и работы с PostgreSQL задаются через переменные окружения:

```text
DATABASE_CONNECT_TIMEOUT
DATABASE_QUERY_TIMEOUT
DATABASE_MAX_CONN_LIFETIME
DATABASE_MAX_CONN_IDLE_TIME
```

HTTP-сервер также использует настраиваемые таймауты:

```text
HTTP_READ_TIMEOUT
HTTP_READ_HEADER_TIMEOUT
HTTP_WRITE_TIMEOUT
HTTP_IDLE_TIMEOUT
```

При остановке сервиса применяется `SHUTDOWN_TIMEOUT`.

### Graceful shutdown

При получении сигнала завершения сервис:

1. прекращает принимать новые HTTP-запросы;
2. корректно останавливает HTTP-сервер;
3. закрывает соединение с базой данных;
4. завершает работу после обработки активных запросов в пределах `SHUTDOWN_TIMEOUT`.
